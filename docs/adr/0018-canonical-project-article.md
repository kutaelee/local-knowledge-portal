# ADR 0018: 프로젝트별 최신 통합 문서

- 상태: Accepted
- 일자: 2026-07-26

## 배경

기존 프로젝트 개발일지는 최근 작업 기록을 주제별로 발췌해 이어 붙였다. 따라서 작업 이력은 남았지만, 프로젝트의 목적·현재 구조·운영 방식·중요한 결정이 하나의 글로 연결되지 않았고 같은 근거가 여러 섹션에 반복됐다.

## 결정

프로젝트마다 `project_article` 한 건을 두고, 실제 본문은 append-only `project_article_revision`으로 관리한다.

- 원문 범위는 현재 활성 상태인 `.md`, `.mdx`, `.txt`, `.rst`와 프로젝트 작업 기록이다. 소스 코드는 원문 탐색과 검색에는 남지만 프로젝트 글의 자동 편집 입력에서는 제외한다.
- 최초 편집에서는 모든 원문 조각을 제한된 크기의 batch로 한 번씩 읽는다. 원문 묶음이 많으면 `원문 묶음 편집 노트 → 편집 노트 묶음 축약 → 최종 통합 글`의 계층형 편집을 반복하여 모델 context 한도를 넘지 않는다.
- 이후에는 이전 source manifest와 비교하여 변경·추가된 원문 본문과 제거된 source ID만 편집기에 전달한다.
- 화면에 표시할 인용 목록과 전체 source manifest를 별도 필드로 보존한다. 따라서 최종 글에서 인용하지 않은 원문도 다음 갱신 때 매번 신규 원문으로 오인하지 않는다.
- 모델·digest·prompt version이 바뀌거나 기존 manifest보다 큰 원문 확장이 생기면 이전 저품질 글에 고정되지 않도록 전체 원문으로 재편집한다.
- 편집기는 patch가 아니라 항상 완성된 최신 글 전체를 반환한다. 아직 유효한 설명은 보존하고, 바뀐 설명은 교체하며, 제거된 근거에만 의존한 문장은 삭제한다.
- 모든 문장은 하나 이상의 정확한 source ID를 가져야 한다. 알 수 없는 ID, 제거된 ID, 근거 없는 문장은 저장하지 않는다.
- 긴 원본 ID는 모델 호출 안에서만 결정론적 별칭(`S0001` 등)으로 바꾸고, 저장 전에 실제 ID로 복원하여 다시 검증한다.
- 각 원문 묶음은 최종 글이나 상위 편집 노트에 최소 한 건의 근거를 남겨야 한다. 묶음 전체가 사라지면 저장하지 않는다.
- 섹션은 개요·구조·흐름·결정·운영·검증·제약·다음 작업의 고정 편집 분류 안에서만 생성하고, 같은 분류는 코드가 하나의 섹션으로 합친다.
- 빈 문단이나 빈 섹션 같은 모델 scaffolding은 결정론적으로 제거하되 문장을 임의로 채우지 않는다.
- 각 리비전에는 provider, model, digest, prompt version, source hash와 변경 통계를 기록한다.
- 사람이 보는 번호는 source ID와 분리하여 글 안에서 처음 인용된 순서대로 매긴다. 번호를 누르면 원본 경로, 문서/버전/chunk ID, 줄 범위와 인용 원문을 표시한다.
- 관리형 Markdown은 Vault의 `_generated/Projects/<project>/project-overview.md`에만 atomic replace로 기록한다. 관리 표식이 없는 파일은 덮어쓰지 않는다.
- 적용 범위는 특정 저장소 이름으로 고정하지 않는다. 현재 활성 문서 또는 프로젝트 작업 기록이 하나라도 있는 모든 `project_key`가 대상이며, 새 저장소가 인덱싱되면 별도 코드 변경 없이 편집 대기열에 들어간다.
- 실행 예산보다 프로젝트가 많아도 이름순 앞부분만 반복하지 않는다. 누락 문서, 중단·실패 재시도, 모델·prompt 변경, 원문 변경 순으로 처리하고 같은 우선순위에서는 가장 오래 확인하지 않은 프로젝트부터 순환한다.
- 각 프로젝트는 모델 호출 전에 `processing` 상태와 확인 시각을 먼저 commit한다. 프로세스가 중단되거나 모델이 실패하면 `error`를 별도 commit하여 다음 예약 실행이 이어받는다.
- 대규모 프로젝트의 원문 묶음 노트는 E 드라이브 cache에 atomic write한다. GPU 작업이 실행 제한에 도달해도 완료된 묶음을 다음 실행에서 재검증·재사용하며 처음부터 다시 생성하지 않는다.

## 결과

프로젝트 화면의 기본 문서는 작업 목록이 아니라 사람이 읽을 수 있는 최신 글이다. 과거 작업은 별도 이력으로 남고, 원문 변화가 없으면 새 리비전이나 모델 호출을 만들지 않는다. 원문 변화가 생기면 이전 글과 비교한 새 리비전이 생성되어 과거 상태와 근거를 추적할 수 있다.

모델은 문맥 편집만 담당한다. source 수집, 변경 비교, 인용 번호, 허용 ID 검증, 리비전 저장, 관리형 파일 갱신은 코드가 담당한다.

프로젝트 화면은 아직 편집되지 않은 레포에 과거 작업 발췌를 완성 문서처럼
표시하지 않는다. `편집 대기`, `편집 중`, `재시도 대기`, `갱신 대기`, `최신`
상태를 구분하며, 검증된 리비전이 생긴 뒤에만 통합 본문을 표시한다.

`include_patterns`는 scanner뿐 아니라 watcher, worker, reconciliation, dead-letter 판정에 동일하게 적용한다. 문서 전용 source root에 코드가 들어온 경우 원본이나 이력을 삭제하지 않고 파생 `document.state`를 `ignored`로 전환한다.

## 편집 범위와 누락 방지

모든 원본 조각은 먼저 작은 근거 묶음별 편집 노트로 변환한다. 중간 노트는 원본 해시, 모델, digest, prompt version을 포함한 키로 E 드라이브 runtime cache에 저장하며, 재실행 때 동일한 검증을 통과한 노트만 재사용한다. 따라서 최종 합성 실패가 전체 원문 재처리로 이어지지 않는다.

최종 글에 모든 원본을 강제로 인용하면 원문 발췌를 이어 붙인 목록이 되므로 금지한다. 대신 모든 원본을 편집 노트 단계에서 읽고, 최종 글은 설정된 비율(기본 45%) 이상의 상위 편집 묶음을 직접 근거로 포함해야 한다. 이 비율은 중복 문서가 많은 실제 원본 묶음에서 동일 사실을 여러 번 인용하도록 강제하지 않으면서도 일부 작업 기록에만 편향된 글을 차단하는 하한이다. 기준에 미달하면 누락 묶음만 최대 3회 보강하며, 근거 묶음 반영 수가 실제로 증가한 결과만 채택한다. 기준에 끝내 도달하지 못하면 새 리비전을 저장하지 않는다.

각 리비전은 화면에 실제로 인용된 `sources_json`과 전체 비교용 `source_manifest_json`을 분리해 보존한다. 새 문서가 추가되거나 기존 문서가 바뀌었는지는 전체 manifest로 판단하고, 독자가 보는 근거 목록에는 본문에서 사용한 출처만 노출한다.
